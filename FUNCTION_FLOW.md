## 二、监控数据采集流程

### 2.1 流程图

```
┌──────────────┐
│  监控Agent   │
│  (psutil)    │
└──────┬───────┘
       │
       │ 1. 采集指标
       │    - CPU使用率
       │    - 内存使用率
       │    - 磁盘使用率
       │    - 服务器基本信息
       ▼
┌────────────────────────┐
│  数据封装与格式化      │
│  - JSON格式            │
│  - 添加时间戳          │
│  - 添加服务器标识      │
└──────┬─────────────────┘
       │
       │ 2. HTTP POST请求
       ▼
┌──────────────────────────┐
│  Flask API: /api/monitor │
│  /data                   │
└──────┬───────────────────┘
       │
       │ 3. 数据校验
       │    - 必填字段检查
       │    - 数据格式验证
       ▼
┌──────────────────────────┐
│  数据存储                │
│  ├─ MySQL: monitor_data  │
│  └─ Redis: 最新数据缓存  │
└──────┬───────────────────┘
       │
       │ 4. 触发告警检查
       ▼
┌──────────────────────────┐
│  告警检查定时任务        │
│  (APScheduler)           │
└──────────────────────────┘
```

### 2.2 详细步骤

| 步骤 | 操作 | 涉及组件 | 说明 |
|------|------|----------|------|
| 1 | 指标采集 | monitor_client.py | 使用psutil采集CPU、内存、磁盘 |
| 2 | 数据发送 | HTTP POST | 发送到Flask后端API |
| 3 | 数据接收 | Flask路由 | /api/monitor/data |
| 4 | 数据存储 | MySQL + Redis | MySQL存历史，Redis存最新 |
| 5 | 告警触发 | APScheduler | 定时检查是否需要告警 |

| 9 | 前端更新 | WebSocket | 页面刷新 |

## 五、Dify工作流执行流程

### 5.1 基础智能告警工作流

```
┌─────────────────────────────────────────────────────────────────┐
│  开始节点                                                         │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点1: 数据校验                                                   │
│  - 检查必填字段是否存在                                            │
│  - 检查数据格式是否正确                                            │
│  - 失败则直接返回不告警                                            │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点2: 趋势分析                                                   │
│  - 计算CPU变化率: (当前 - 5分钟前) / 5分钟前 * 100%             │
│  - 判断趋势: rising/falling/stable                                │
│  - 检查是否持续告警: 过去5分钟是否持续超过阈值                     │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点3: 条件判断 - 快速上升检测                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  IF CPU变化率 > 30% AND CPU > 80%:                            │ │
│  │     → 严重告警分支                                              │ │
│  │  ELSE:                                                          │ │
│  │     → 继续下一步判断                                            │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点4: 条件判断 - 多指标组合                                     │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  IF CPU > 80% AND 内存 > 75%:                                 │ │
│  │     → 紧急告警 (emergency)                                      │ │
│  │  ELSE IF CPU > 90% OR 内存 > 90%:                             │ │
│  │     → 严重告警 (critical)                                       │ │
│  │  ELSE IF CPU > 70% OR 内存 > 70%:                             │ │
│  │     → 警告 (warning)                                            │ │
│  │  ELSE:                                                          │ │
│  │     → 不告警                                                    │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点5: 日志分析 (可选)                                           │
│  - 统计ERROR数量: related_logs.error_count_last_10min            │
│  - 检查关键异常: timeout/error/slow query                         │
│  - 如果有大量ERROR，提升告警级别                                   │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点6: 静默期检查                                                 │
│  - 查询最近告警记录                                                 │
│  - 判断是否在静默期内                                               │
│  - 如果在静默期，设置should_alert=false                           │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点7: 生成告警原因                                               │
│  - 根据分支选择不同的原因模板                                      │
│  - 填充具体数值                                                    │
│  - 例如: "CPU从55%快速上升到85%，持续5分钟"                      │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点8: 生成处理建议                                               │
│  - 根据告警级别给出建议                                            │
│  │  critical: 建议立即检查数据库慢查询/异常进程                   │ │
│  │  warning: 建议关注，观察趋势                                   │ │
│  - 列出具体操作步骤                                                │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  节点9: 生成邮件内容                                               │
│  - 生成邮件主题                                                    │
│  - 生成邮件正文                                                    │
│  - 包含指标、告警原因、处理建议                                    │
└──────────────┬────────────────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  结束节点                                                         │
│  - 输出完整决策结果                                                │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 主要页面数据流

#### 实时监控页面 (/monitor)
```
前端定时轮询 (每5秒)
    ↓
GET /api/monitor/recent
    ↓
Flask从Redis获取最新数据
    ↓
返回JSON: {cpu, memory, disk, timestamp}
    ↓
前端更新ECharts图表
```

#### 日志检索页面 (/logs)
```
用户输入搜索条件
    ↓
POST /api/logs/search
    ↓
log_service.search_logs()
    ↓
查询Elasticsearch
    ↓
返回日志列表
    ↓
前端表格展示
```

#### Dify决策记录页面 (/decisions)
```
页面加载
    ↓
GET /api/dify/decisions
    ↓
查询MySQL dify_decisions表
    ↓
返回决策记录列表
    ↓
前端展示
    ↓
点击查看详情
    ↓
GET /api/dify/decisions/{id}
    ↓
返回完整决策详情
    ↓
展示输入数据、决策结果、日志关联
```

## 八、异常处理流程

### 8.1 Dify调用失败降级

```
调用Dify API
    ↓
成功?
    ├─ 是 → 使用Dify决策结果
    │
    └─ 否 → 降级方案
              ↓
         使用原硬编码告警逻辑
              ↓
         记录错误日志
              ↓
         继续执行告警动作
```

### 8.2 ES不可用降级

```
查询ES相关日志
    ↓
ES可用?
    ├─ 是 → 返回查询结果
    │
    └─ 否 → 降级方案
              ↓
         返回空日志列表
              ↓
         Dify工作流继续执行
              ↓
         仅使用指标进行决策
```

## 总结

本文档详细描述了系统的完整功能流转，包括：

1. **监控数据采集** → Flask处理 → MySQL/Redis存储
2. **日志采集** → Filebeat/Docker API → Elasticsearch存储
3. **告警触发** → 准备数据 → 调用Dify → 执行决策
4. **Dify工作流** → 多条件判断 → 智能决策 → 输出结果
5. **前端展示** → API调用 → 数据可视化

所有流程都考虑了异常降级方案，确保系统稳定性。
